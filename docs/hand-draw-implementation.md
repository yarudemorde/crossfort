## 実装方式

`drawCard()`は従来通り、山札からカードを取り出し、その場で実際の手札に追加して、相手のドロー反応を解決します。ゲームロジックの順序・上限8枚・効果の非同期処理は維持。表示用の`handView`は戦闘stateから分離しています。

通常ドローだけ`queueHandDraw()`で短い表示待ちを登録。既存の`renderHand()`はカードのオブジェクト実体をMapのキーにして同じカードDOMを再利用します。同名カードも別実体として区別します。タイマー待ちの新カードは表示上のみ待機させ、開始時に既存の幅と配置式で右端に配置します。

新カードは手札領域の右端より12px外側から、Web Animations APIのCSS transformで260msかけて移動。移動中はz-indexを40にし、終了後は通常の重なりに戻します。回転・拡大・強い発光・効果音はありません。

既存カードは表示位置を前後で比較するFLIP方式で210msの位置調整を行います。頻繁な再描画では同じカードDOMと進行中アニメーションを維持し、追加ドローで移動先が変わる場合はその時点の表示位置から残り時間で移動します。毎フレームのレイアウト計算はしません。

2〜3枚の連続ドローは開始を90msずつずらします。多数の場合は後半を45ms間隔に短縮し、開始待ちを420ms以内に制限。最大8枚でも全体約0.7秒程度です。効果解決や次のターンの処理に、この表示時間をawaitさせません。

`handDrawBusy()`によって演出中の手札のタップ・キーボード選択を防ぎます。アニメーションの完了・カード消失・戦闘終了・画面移動ではタイマーとアニメーションを解除し、入力ガードも解除します。ゲームの`state.animating`は演出のために変更しません。

## 適用範囲

- プレイヤーの共通`drawCard()`経由：通常、スペル、ユニット、ランドマークのドロー。
- 初期5枚は`{animate:false}`で除外。
- CPU側のドローは対象外。
- ローカル対戦はplayer側の手札が表示されている間だけ適用。画面側が切り替わる場合はキャンセル。
- 墓地回収、バウンス、手札生成、デッキ編集などの直接追加は対象外。
- `prefers-reduced-motion`有効時、またはWeb Animations API非対応環境では即時表示。

## 動作確認

Chromium実ブラウザの22項目がすべてPASS。以下を確認しています。

- 初期5枚に演出なし。
- 1枚ドローの右→左移動と260ms設定、既存カードDOMの維持。
- 再描画中に進行中の演出が失われない。
- 演出中は誤選択できず、終了後は選択・使用できる。
- スペルによる2枚ドロー＋1枚追加の90ms時間差、手札順序と上限8枚。
- 0→1枚、7→8枚、満杯時は山札も手札も変更せず演出なし。
- 白龍エルレハイヌの3枚ドロー、黄金色の聖杯の1枚ドロー。
- 8枚ドロー時の表示開始待ち短縮。
- CPUドローでプレイヤーの手札が動かない。
- プレイヤーのターン開始ドロー。
- 戦闘終了・ホームへ移動時のキャンセル。
- 低モーション時の即時表示、通常の直接手札追加に演出なし。
- 360×640、390×844、430×932、1280×800で、移動中・終了後とも横はみ出しなし。

既存のAI・第三弾青・防衛線・キーワード表示・ランドマーク・月神・シーズンスコアのロジック回帰テストと、シーズン終了までのブラウザ検証も実施。実際のiPhone端末での確認は未実施です。
